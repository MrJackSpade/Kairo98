# KairoDos feasibility study

27 September 2026. This is a design recommendation, not an imported core, build, or release audit.

## Recommendation

Maintain **one Android frontend codebase** and two emulator adapters. Kairo98 and a possible KairoDos can live in separate product repositories, each with its own GitHub Pages site and release pipeline. A first-party `Kairo` repository owns the shared frontend Android library: activity flow, library and detail views, session UI, rendering surface, Android input collection, storage access, and secondary-display behavior. Each product pins that library as a Git submodule and owns its backend and app-specific policy. This user-directed shared-code submodule replaces the earlier no-submodule constraint for that dependency; emulator source snapshots remain in each product's `third_party/` rather than becoming upstream submodules.

Two APKs are my current product recommendation because they preserve Kairo98's PC-98 identity, let users install them independently, and keep the DOS core's GPL distribution obligations on the DOS app. **They must not become two independently maintained frontends.** If a unified Kairo app and library is more valuable than separate products, one APK with a runtime backend selector could require even less packaging and release work. It would make the whole combined APK subject to GPL-compatible distribution terms and require deliberate mixed-system library, settings, and support behavior.

Use **DOSBox Pure as the initial DOS base**, with performance as the overriding reason to reconsider it. The long-term decision is about the health of the code we would actually ship on Android, not just the health of an upstream repository in isolation. Staging has the strongest visible engineering and team practices, but its supported builds are desktop applications and an Android port would become our permanent responsibility. Pure's upstream is more dependent on one lead maintainer, yet it is active, has recent Android-specific maintenance, and already exposes the host boundary KairoDos needs. DOSBox-X is active and receives contributions from several people, but its broad machine-emulation scope and unsupported Android target would leave us maintaining a larger port. The original DOSBox remains foundational but has a much slower packaged-release cadence. The public evidence does not establish a clear ARM64 Android throughput winner among Pure, Staging, and X; all three have ARM64 dynamic-recompiler support. If representative games fall short on target devices, compare another core before trying to optimize Pure internally. Lawful GPL redistribution is a business consideration, not a stated veto.

## Options

| Design | Long-term frontend maintenance | Other cost |
| --- | --- | --- |
| One APK with two backends and one frontend | One frontend | One release path and user library, but every distributed build containing the DOS core becomes GPL-covered; mixed-system UX and settings grow. |
| Two APKs with one shared frontend module in `Kairo` | One frontend | Two product repositories, package IDs, store listings, release artifacts, and separate app data. Each product pins and tests a shared commit. Recommended for the two-product idea. |
| Two independently copied frontends | Two frontends | Duplicate feature and bug work. Avoid. |

The two-app design can preserve the existing rule that Kairo98's free GitHub and paid Play builds have the same features and behavior, while applying the same rule to KairoDos. The apps can use different package IDs and install side by side. Separate Android packages do not automatically share user files, preferences, or save states; any cross-app import would need an explicit user-mediated flow. Shared frontend source means a library or controller UI fix is made once and built into both products.

### Candidate cores

| Core | Performance-relevant evidence | Integration tradeoff |
| --- | --- | --- |
| [DOSBox Pure](https://github.com/schellingb/dosbox-pure) | Its [configuration](https://github.com/schellingb/dosbox-pure/blob/main/include/config.h) enables the ARM64 `C_DYNREC` backend; `auto` uses the interpreter for real-mode games and dynarec for protected-mode games. Its [preview release](https://github.com/schellingb/dosbox-pure/releases) reports faster 3dfx rendering with OpenGL on Android, a workload-specific result. | Libretro API gives a small host surface. The project has a strict policy against AI-generated upstream contributions; follow it for any issue or patch sent there. |
| [DOSBox Staging](https://github.com/dosbox-staging/dosbox-staging) | Its [CPU manual](https://www.dosbox-staging.org/0.83/manual/system/cpu/) documents a dynamic recompiler and the real-mode/interpreter default. An [ARM64 dynarec development report](https://github.com/dosbox-staging/archived-discussions-for-dosbox-staging/discussions/2) measured a large gain over the interpreter on one Mac workload; that is not an Android or cross-core result. | Published release platforms are desktop; [build dependencies](https://github.com/dosbox-staging/dosbox-staging/blob/main/docs/build-linux.md) make an Android host port larger. |
| [DOSBox-X](https://github.com/joncampbell123/dosbox-x) | Its [build configuration](https://github.com/joncampbell123/dosbox-x/blob/master/configure.ac) recognizes ARM64 and its [reference configuration](https://github.com/joncampbell123/dosbox-x/blob/master/dosbox-x.reference.conf) exposes a dynamic CPU core. One [2023 project benchmark](https://github.com/dosbox-staging/dosbox-staging/issues/2284) reported about 189 FPS for X versus 211 FPS for Staging in Quake on a desktop host; this cannot rank Android builds. | Broad machine coverage and extensive desktop host integration mean a larger Android host replacement. |
| [Bochs](https://github.com/bochs-emu/Bochs) | Different product direction | Its project license is LGPL-2.1, which can permit a proprietary frontend under its conditions. It is a full x86 machine emulator, not a DOSBox-compatible ready-to-run DOS environment. Android integration, guest OS supply, performance, replaceable-library obligations, and all transitive licenses would need investigation. It is not the leading prototype. |

The distinction is **upstream health versus the maintenance burden of our shipped Android build**. Staging wins the first; Pure wins the combined decision for this app today. This is a judgment from published project activity and platform support, not a claim that Pure is faster or immune to maintainer turnover. Keep our Android session contract independent of libretro, pin and audit each adopted Pure snapshot, keep local core patches small and documented, and preserve a buildable known-good snapshot. Revisit the core only for measured game failures, prolonged upstream inactivity, a major Android compatibility break, or an unmanageable local patch set. Do not import upstream through a Git remote or automated merge.

## What this repository can reuse

The Kairo98 Gradle build now has `:kairo98` and a pinned `:frontend` library. `MainActivity.kt` still contains both UI navigation and PC-98 JNI calls. The CMake build compiles the pinned 21/W snapshot and ymfm into `libkairo98.so`. This is the first extraction step; there is no backend interface to plug DOSBox into today.

| Reuse with modest changes | Keep specific to each app |
| --- | --- |
| `Ui.kt`, library and detail screen layout, overlay/menu structure, physical controller discovery, on-screen control arrangement, secondary-display shell, viewport scaling, Android storage picker patterns | PC-98 keyboard layout and scan codes, `InputModeDecider` telemetry, YM2608/BIOS/font setup, `DiskFormat` and boot-pair logic, PC-98 catalog and startup automation, `state.np2` save format, core-native JNI bridge |

Some apparently reusable files contain PC-98 semantics today. `ControllerBindings.kt` stores numeric PC-98 scan codes, `RomLibrary.kt` recognizes PC-98 disk-image extensions, and `StateSlots.kt` names a 21/W state file. Share the UI machinery, not those data formats. KairoDos needs its own concept of one game (folder, ZIP, executable with working directory, CD image, or playlist), DOS keyboard mapping, configuration, write overlay, and state identity.

## Proposed boundary

```text
Kairo repo      :frontend activity/navigation, library/detail UI, input shells,
                secondary display, viewport, storage UI, session/lifecycle contract
Kairo98 repo    :kairo98 + :backend-pc98; pinned Kairo submodule; libkairo98.so,
                PC-98 catalog, machine settings, keymap, and states
KairoDos repo   :kairodos + :backend-dos; pinned Kairo submodule; DOSBox Pure,
                DOS content, machine settings, keymap, and states
```

The concrete extraction, build, persistence, and validation steps are in [the shared-frontend plan](kairo-dos-shared-frontend-plan.md).

Give the shared frontend a small session contract: start/stop, pause, reset, frame presentation, audio, key/mouse/controller input, media change, and optional state capabilities. Keep guest key names, valid media, machine options, state format, and catalog metadata behind backend capabilities. Avoid `if (dos)` branches throughout the frontend: an app target supplies a backend and its capabilities when the shared activity starts. DOS video modes and pixel aspect ratios can change during a session, so the renderer must accept dynamic geometry rather than assume Kairo98's 640 x 400 surface. Save-state support should be advertised by the backend and tested per game; [DOSBox Pure warns](https://docs.libretro.com/library/dosbox_pure/) that complex games and changed CPU or video settings can invalidate states.

For DOSBox Pure, implement only the libretro frontend services the pinned core actually requests. Drive `retro_run` on a dedicated emulation thread; connect video and audio callbacks to Android output; map Android keyboard/mouse/controller events into libretro input; provide stable content, system, save, and configuration directories. Keep the shared Android session contract independent of libretro so a demonstrated performance problem can justify another core later. Bundle the reviewed native core in the APK/AAB rather than downloading executable code at runtime; [Google Play's device and network abuse policy](https://support.google.com/googleplay/android-developer/answer/16559646) restricts downloading `.so` files from outside Play.

## License and distribution gate

The [original DOSBox project](https://sourceforge.net/projects/dosbox/) is GPLv2; this is not a condition unique to Pure. DOSBox Pure is [GPL-2.0-or-later](https://github.com/schellingb/dosbox-pure/blob/main/LICENSE), and [DOSBox Staging](https://github.com/dosbox-staging/dosbox-staging/blob/main/LICENSE) is also GPL-2.0-or-later as a compiled whole. A libretro adapter and frontend integrated with a GPL DOS core should be planned as one GPL-compatible, source-available distributed program; putting the core in a separate `.so` does not itself isolate the license. The [GNU GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#GPLStaticVsDynamic) explicitly treats static and dynamic linking alike for combined works. Kairo98, KairoDos, and the first-party shared frontend have now been assigned GPL-2.0-or-later terms. Their separate repositories and the submodule boundary do not change the corresponding-source obligation for a distributed binary. Have the exact snapshot, transitive licenses, generated assets, notices, build scripts, and corresponding source audited before distribution.

**Selling KairoDos is allowed.** The [GNU GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#DoesTheGPLAllowMoney) explicitly permits charging for copies. Buyers must receive GPL rights and access to the complete corresponding source for the delivered binary; they may redistribute their copy, including for free. The [GPL FAQ on paid distribution](https://www.gnu.org/licenses/gpl-faq.html#DoesTheGPLRequireAvailabilityToPublic) says the seller need not offer the binary to everyone for free. This project's separate free GitHub/paid Play parity rule would still call for both channels to have the same KairoDos features and behavior if that model is adopted. Play supports [paid app pricing](https://support.google.com/googleplay/android-developer/answer/6334373), but its terms and the exact distribution method should be reviewed at release time. Revenue would come from the Play installation/update channel and voluntary support, not exclusive control of redistribution.

**Selling while banning reskins or resale of the GPL-covered code is not available under that license.** The [GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#DoesTheGPLAllowRequireFee) says recipients may redistribute without paying the original distributor, and the [GPLv2 text](https://www.gnu.org/licenses/old-licenses/gpl-2.0.html) forbids further restrictions on those rights. Packaging the core as a separate native library in the same app or dynamically loading it does not resolve the combined-work issue according to the [GNU FAQ on linking](https://www.gnu.org/licenses/gpl-faq.html#GPLStaticVsDynamic). The KairoDos name, official logo, and developer identity can be addressed separately through trademark and impersonation protections, but that cannot stop an honestly rebranded code fork. [Google Play's impersonation policy](https://support.google.com/googleplay/android-developer/answer/9888374) addresses misleading names, icons, descriptions, and claims of affiliation. A lawyer should review the exact asset and trademark arrangements before release.

The two-APK/shared-frontend architecture does not itself change this right: if the shared frontend code is distributed as part of a GPL KairoDos app, recipients can exercise the GPL rights they received for that combined distribution. The author may still separately license code they own for Kairo98, but that does not revoke rights already given to KairoDos recipients. This is the tradeoff to accept if the DOSBox Pure prototype succeeds.

If resale protection later becomes a firm requirement, a permissive or LGPL core or an original DOS backend would need separate feasibility work. [Bochs](https://github.com/bochs-emu/Bochs) is one LGPL-2.1 research lead, but it brings a different product and maintenance profile. An independently licensed launcher for an external emulator would also be a different product, and whether two programs are genuinely separate depends on their actual integration.

Apply the repository's source policy to KairoDos: import a pinned and audited snapshot into `third_party/`, record provenance in `docs/source-import.md` and licenses in `docs/licensing.md`, keep only this project's `origin`, and do not bundle game files, operating systems, proprietary firmware, or optional sound-module ROMs. Keep fmgen excluded from Kairo98 distributable builds. Do not claim either app's binary is release-ready before an Android device boots a game and its artifact-specific license audit is complete.

## Smallest useful proof

1. Import one pinned and audited DOSBox Pure snapshot into `third_party/`, record provenance and licenses, and build a thin arm64 libretro host. Confirm that the ARM64 dynamic recompiler is active for a protected-mode game on the target Android device.
2. Play a few representative legally held DOS games on the target device, including real-mode, protected-mode, graphics-heavy, and audio-heavy cases. Check sustained full-speed play, stable sound, frame pacing, and whether the device throttles during a longer session. Use unpacked content for any core-performance check so ZIP work is not mixed into the result.
3. If one of those games misses its performance target, compare that same workload against Staging or X at equivalent CPU, video, and audio settings before spending time optimizing Pure. Otherwise, keep Pure and proceed.
4. Move the existing activity flow and UI into `:frontend` with a backend/session and product-capability contract. Keep Kairo98 working through its adapter, add the DOS adapter, then verify Android lifecycle, input, display-mode changes, disc control, persistent writes, and save/load on device. Build matching GitHub and Play variants from one revision and audit the exact artifacts before any release claim.

No DOSBox candidate has yet been built or measured by this project. The public sources reviewed do not show a decisive ARM64 Android performance gap that would justify a broad comparative benchmark before the first prototype.
