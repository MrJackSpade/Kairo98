# Artwork intake

Each packaged image needs a source file, SHA-256, creator, source, license or permission basis, and evidence that redistribution is allowed in both the free GitHub build and the paid Google Play build. Resizing and recompression also need to be allowed. `tools/import_art.py` refuses records without those affirmative flags and verifies the source digest before creating a bounded WebP asset. Its generated `art/provenance-v1.json` travels with the assets.

The two PNGs in `docs/fixtures/art-source/` are original synthetic test fixtures created for this project. They contain no game screenshot or publisher box art. The project can bundle and resize these fixtures in both distribution channels. Their source hashes and this permission basis are recorded in the fixture manifest. They test the import path for one synthetic content ID; they do not imply permission for any real game media.

LaunchBox's [Games Database media guide](https://feedback.launchbox-app.com/en/help/articles/7997304-using-games-database-media-in-launchbox) describes downloading images into a local LaunchBox library, and its [database introduction](https://feedback.launchbox-app.com/en/help/articles/8890692-getting-started-with-the-launchbox-games-database) describes a community-maintained collection. Those pages do not grant Kairo98 permission to redistribute every database image in another app. A candidate LaunchBox image stays out of release inputs until its creator or rights holder's applicable terms permit both builds and the intended transformation. Keep a separate record per asset because screenshot, box scan, and fan art rights may differ.

The first [candidate inventory](art-candidates.md) records a box front and screenshot for the known test title, with creator and redistribution rights still unverified. Neither candidate is packaged.

Build order: generate catalog shards with `tools/build_catalog.py`, then run `tools/import_art.py docs/fixtures/art-source/source-v1.json app/src/main/assets` for the approved fixture. The importer updates only matching catalog records, adds content-deduplicated WebP files, and writes provenance plus a coverage and packaged-byte report. The current fixture covers one synthetic catalog game with one box image and one preview; the two WebP files total 5,338 bytes. Library rows decode art on a worker thread, and a missing or unreadable image falls back to the resolved game title. Catalog title falls back to the filename when no record matches.

The importer stages conversions before modifying packaged files. A rejected record leaves existing catalog and art files intact. On a later approved-manifest update, it removes references and generated WebP files for assets no longer present; the catalog generator also removes obsolete generated shards. The importer requires provenance when an art directory already contains WebP files so unknown files are not silently adopted.
